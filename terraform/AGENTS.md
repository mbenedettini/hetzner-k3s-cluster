# Terraform Guidance

Terraform has two independent root stacks. There is no root module directly in
`terraform/` or at the repository root.

## Stacks And Modules

- `terraform/staging`: Hetzner network, server, and K3s bootstrap resources.
- `terraform/cloudflare`: Cloudflare R2-backed container registry resources.
- `terraform/modules`: shared modules consumed by the Hetzner stack.
- Both stacks use the same S3-compatible state bucket with distinct object
  keys. Never copy state or backend configuration between them casually.

Always select a stack explicitly:

```bash
terraform -chdir=terraform/staging fmt -check
terraform -chdir=terraform/staging init -backend=false
terraform -chdir=terraform/staging validate

terraform -chdir=terraform/cloudflare fmt -check
terraform -chdir=terraform/cloudflare init -backend=false
terraform -chdir=terraform/cloudflare validate
```

The Cloudflare stack has an additional external bundle prerequisite described
in its local `AGENTS.md` and README.

## Safety

- Do not run `apply`, `destroy`, `taint`, `import`, state commands, or
  replacement operations without explicit authorization.
- Before an authorized apply, present the plan and call out every replacement,
  deletion, and externally visible change.
- Never inspect or commit `secrets.auto.tfvars`, SSH keys, `.terraform/`, local
  state, plan files containing sensitive values, or generated credentials.
- `.terraform.lock.hcl` is generated by Terraform. Change it only through an
  intentional provider initialization or upgrade.
- Treat cloud-init inputs and outputs as sensitive because rendered user data
  can contain credentials.

## Module Changes

- Keep module interfaces in variables and outputs rather than coupling callers
  to module internals.
- Preserve provider alias requirements used by `hcloud-network`.
- Validate a module through every consuming root stack.
- Treat `modules/cloud-init` as replacement- and credential-sensitive cluster
  bootstrap code. cloud-init is primarily a first-boot mechanism; a template
  change does not safely reconfigure an existing node by itself.
- Coordinate network addresses, interface assumptions, and Kubernetes API
  endpoint changes with the root and stack-local kubeconfig templates.
- `worker-cloud-init.yaml` handles an SSH private key that can be persisted in
  rendered user data and Terraform state. Do not expose rendered output or
  plans containing it.
- K3s is configured for an external cloud provider, but the Hetzner Cloud
  Controller Manager installation is not declared in this repository.
- Review whether every cloud-init change affects only future nodes or requires
  an explicit migration for existing nodes.

The current Terraform GitHub Actions workflow runs `init` and `validate` at the
repository root, where no root module exists. Do not treat that job as proof
that either actual stack validates successfully.
